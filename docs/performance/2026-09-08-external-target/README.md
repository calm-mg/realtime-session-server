# 운영 서버와 부하 생성기의 프로세스·CPU 분리 측정

외부 IPv4 대상 모드를 사용해 `rss_server`와 부하 생성기를 별도 프로세스로
실행했습니다. 서버에는 CPU 0–1, 부하 생성기에는 CPU 2–3을 배정했습니다.
원시 명령, 서버 NDJSON 로그, 클라이언트 출력과 종료 코드는
[results.json](results.json)에 보관합니다.

## 환경과 절차

- 소스: `fe8ff3bc3858d9e552935de23479c37e0d0080db`, 깨끗한 작업 트리
- 빌드: GCC 13.3.0 Release, sanitizer 비활성. 두 실행 파일 SHA-256은 원시 결과에 기록
- 실행 환경: Linux arm64 컨테이너, Ubuntu 24.04, CPU quota 4개·메모리 4 GiB
- 서버: 별도 `rss_server` 프로세스, worker 2개, CPU affinity 0–1
- 부하 생성기: CPU affinity 2–3, 같은 Linux VM의 loopback TCP
- DB: 별도 PostgreSQL 16.15 컨테이너, CPU affinity 0–1·quota 1개·메모리 1 GiB
- 영속화: 로그인 시 사용자 UUID 저장·조회. 채팅 자체는 DB에 저장하지 않음
- 시나리오: 정상 20명, 단일 방 또는 4개 방, client별 300건·10건/초 상한,
  방별 window 8건, payload 256byte, 제한 시간 60초
- 반복: 조건마다 서버를 시작하고 warm-up 1회 후 측정 3회. 한 조건의 반복은
  같은 서버를 유지하며 새 TCP 연결과 고유한 이름 사용
- 서버 통계: 10초 주기와 SIGTERM 정상 종료 시 최종 snapshot 수집

[외부 서버 실행 절차](../../benchmark.md#외부-서버와-분리-실행)의 명령을
사용합니다. 다중 방은 `--scenario multi-room --rooms 4`를 지정합니다.
서버와 부하 생성기의 CPU 배정을 적용하려면 실행 환경에서 해당 CPU 번호를
사용할 수 있어야 합니다.

## 관측 결과

클라이언트 측정 6회 모두 종료 코드 0이고 기대 수신과 실제 수신이 일치합니다.
서버 프로세스도 두 조건 모두 정상 종료 코드 0을 반환했습니다.

| 조건 | 회당 송신 / 수신 | 경과 시간(초) | 수신 broadcast/초 | p95(ms) | p99(ms) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 단일 방·20명 | 6,000 / 120,000 | 30.381–30.649 | 3,915–3,950 | 28.393–29.795 | 40.639–41.287 |
| 4개 방·각 5명 | 6,000 / 30,000 | 30.268–30.701 | 977–991 | 41.177–41.957 | 44.544–69.004 |

각 범위는 반복별 값의 최솟값–최댓값입니다. 누락·중복·예상 밖 수신과
클라이언트 단계별 실패는 6회 모두 0입니다. 서버 최종 snapshot의 입력
queue 포화·출력 예산 거절·handler 예외·worker 세션 실패도 두 조건 모두
0이고, 남은 연결 및 입력·출력 queue 크기는 0입니다.

서버 종료 원인은 단일 방에서 상대 EOF 80건, 다중 방에서는 상대 EOF 79건과
소켓 오류 1건입니다. 총 80건은 warm-up과 측정 3회의 client 20명에 대응합니다.
다중 방의 소켓 오류는 첫 측정 반복이 끝난 뒤 다음 반복으로 넘어간 시점의
누적 snapshot에서 처음 관측됩니다. 클라이언트 성공 판정만으로 서버의
모든 종료가 EOF였다고 해석하지 않습니다. 주기 snapshot만으로 정확한 오류
발생 시점이나 errno를 확정할 수 없습니다.

별도 진단에서 작은 다중 방 조건을 시스템 호출 추적과 함께 30회·100회
반복했으나 소켓 오류는 재현하지 못했습니다. worker 4개·무제한 송신 등
[진단 조건과 요약](diagnostics.json)을 별도로 기록했습니다. 지연과 송신량이 원래 조건과
다르고 추적 자체도 타이밍에 영향을 주므로 원래 관찰을 무효화하지 않습니다.
원인을 확인하지 못한 1건은 [알려진 문제](../../known-issues.md)에 추적합니다.

단일 방의 p99 약 41ms는 CPU 집합을 분리해도 관측됐고, 다중 방 첫 반복의
p99는 69.004ms였습니다. 이 측정만으로 TCP 지연, 스케줄링이나 mutex 중
어느 원인이 지배적인지는 판단하지 않습니다.

## 해석 범위

클라이언트 결과의 `server_stats=unavailable`은 미수집 상태입니다. 서버의
카운터가 0이라는 뜻이 아닙니다. 별도 NDJSON 최종 통계는 warm-up과 모든
측정 반복·준비·연결 정리를 포함한 서버 수명 전체의 누적 값입니다. 각 run의
종료 통계로 대입하지 않습니다. 클라이언트 환경 줄도 서버 환경을 나타내지
않습니다.

CPU affinity는 두 실행 프로세스의 CPU 집합을 분리하지만 물리 머신, VM,
메모리와 네트워크 커널은 공유합니다. DB는 서버 측 CPU 집합을 공유합니다.
외부 물리 머신의 독립 부하 생성 결과는 아닙니다.

이전 내장 서버 기준값과는 CPU 배정, 서버 프로세스 구성과 PostgreSQL 로그인
경로가 달라졌습니다. 따라서 직접적인 개선 전후 비교로 사용하지 않습니다.
rate/window 대기 시간은 송신→수신 지연 표본에 포함되지 않으며, 이 결과는
설정한 낮은 부하의 회귀 기준값입니다. 최대 처리량·동시 접속 한계나 장시간
안정성을 입증하지 않습니다.

외부 모드에서는 느린 연결의 종료 원인을 자동으로 수집하지 않으므로
`slow-client` 시나리오는 지원하지 않습니다. 이 검증은 기존 내장 서버 모드를
유지합니다. 다음 단계는 TCP 송수신 지연과 `RoomService` mutex 경합을 각각
측정해 실제 병목을 분리하고, 근거가 확인되면 개선 전후를 비교하는 것입니다.
