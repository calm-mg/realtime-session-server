# 외부 다중 방의 지연과 RoomService mutex 분석

기존 p99 약 41–69ms를 TCP 패킷과 한 변수 비교로 조사했습니다. 서버의
Nagle 동작과 클라이언트 delayed ACK가 겹치는 약 40ms 전송 대기를 확인했습니다.
서버에만 TCP_NODELAY를 적용한 진단 실행에서 이 구간이 줄었고, 클라이언트에만
적용한 실행에서는 남았습니다. 운영 코드의 기본 설정은 이 조사에서 바꾸지
않았습니다. 아래 진단 소스는 원인 분리용 임시 코드이며 제품 구현이 아닙니다.

## 조건과 원시 자료

기준 소스는 `cd0cf652f6b43bb42f331ed713181ea9cad11567`입니다. Ubuntu 24.04
arm64, GCC 13.3.0 Release, Linux 5.15.49-linuxkit-pr와 별도 PostgreSQL 16.15를
사용했습니다. 서버는 CPU 0–1과 worker 2개, 부하 생성기는 CPU 2–3이며 같은
Linux VM의 loopback으로 통신합니다. 실행 컨테이너는 CPU quota 4개·메모리
4 GiB, DB는 CPU 0–1·quota 1개·메모리 1 GiB입니다. 준비한 임시 DB의 사용자
테이블을 사용했고 채팅 자체는 DB에 저장하지 않습니다.

조건은 client 20명, 방 4개, client별 300건, payload 256바이트,
rate-per-client 10, max-in-flight 8, timeout 60초입니다. 각 조건마다 새 서버를
시작하고 warm-up 1회 뒤 측정 3회를 수행했습니다. 서버 NDJSON은 10초 주기와
SIGTERM 종료 시 수집했습니다. 조건은 순차 실행했고 빌드·테스트를 측정과
동시에 실행하지 않았습니다. CPU affinity는 물리 머신과 커널의 분리를 뜻하지
않습니다.

[results.json](results.json)은 실행 명령·원시 클라이언트 출력·서버 로그와
실행 파일 해시를 보관합니다. `commit=unknown`은 소스 mount 빌드의 환경
표시이므로 위 기준 소스와 해시를 함께 사용합니다. mutex 빌드만 별도 소스
사본의 RoomService 잠금을 계측했습니다. TCP 설정 비교는 같은 실행 파일에
accept4 또는 connect wrapper를 LD_PRELOAD로 주입했습니다. 대상 소켓의
TCP_NODELAY 설정 실패는 실행 실패로 처리했습니다.

[experiments.json](experiments.json)에 임시 진단 소스와 빌드·실행 방법,
[packet-analysis.json](packet-analysis.json)에 TCP stream에서 복원한 메시지의
시각 비교와 표본 수를 기록했습니다. 패킷 캡처의 kernel drop과 분석 coverage도
함께 확인해야 합니다. 진단 프로그램은 loopback IPv4, microsecond pcap,
이 프로토콜의 프레임을 전제로 하므로 범용 분석기로 사용하지 않습니다.

네 캡처의 kernel drop은 모두 0이지만, `baseline-1`에서 복원한 응답은
119,974/120,000개입니다. 측정 run 3은 29,974/30,000개, 최초 응답 통계는
5,996/6,000개 요청을 포함합니다. 이 조건의 패킷 백분위는 복원 표본에 한정하며
완전 수집으로 해석하지 않습니다. 이후 캡처는 종료 전 1초 대기를 추가했고
나머지 세 조건에서 각각 요청 24,000개·응답 120,000개를 복원했습니다.
클라이언트 원시 결과의 실제 수신 수는 이 분석 coverage와 별개입니다.

## 패킷에서 확인한 전송 대기

기준 실행의 client port 57650에서 다음 순서를 관측했습니다. 시각은 Unix
초이고 캡처 해상도는 마이크로초입니다.

| 시각 | 방향 | 내용 |
| --- | --- | --- |
| 1788845789.146075 | client → server | 채팅 요청 260바이트 |
| 1788845789.146202 | server → client | 앞선 broadcast 387바이트 |
| 1788845789.186479 | client → server | 위 387바이트까지 ACK |
| 1788845789.186495 | server → client | 대기하던 broadcast를 포함한 778바이트 |

앞선 데이터의 ACK까지 40.277ms, ACK 뒤 다음 데이터까지 16µs였습니다.
대상 채팅 요청에서 해당 broadcast까지의 패킷 시각 차이는 40.420ms입니다.
[추출 pcap](delayed-ack.pcap)과 분석 JSON에는 sequence/ACK 번호 및
`run=0;sender=12;seq=1`의 메시지 대응이 있습니다. 추출 파일은 이 연결의
해당 구간만 보존합니다. 캡처 파일 안의 이름·UUID는 임시 부하 데이터입니다.

이 흐름과 서버 측 TCP_NODELAY 대조 실험을 함께 사용해 원인을 판단했습니다.
[tcp(7)](https://man7.org/linux/man-pages/man7/tcp.7.html)에 따르면 TCP_NODELAY는
작은 송신을 모으는 Nagle 동작을 끕니다. TCP_QUICKACK은 지속 설정이 아니므로
이번 대조에서는 사용하지 않았습니다. syscall 진입 시각을 직접 기록한 것은
아니므로 ACK 이전의 각 send 호출 시각까지 이 패킷만으로 확정하지 않습니다.

## TCP 설정 대조 결과

| 조건 | p95 범위(ms) | p99 범위(ms) |
| --- | ---: | ---: |
| 기준, 캡처 | 1.978–40.488 | 41.894–55.073 |
| 서버만 TCP_NODELAY, 캡처 | 1.489–1.576 | 3.325–11.792 |
| 클라이언트만 TCP_NODELAY, 캡처 | 29.155–41.085 | 41.964–43.042 |
| 기준, 캡처 없음 | 40.056–40.796 | 44.227–45.643 |
| 서버만 TCP_NODELAY, 캡처 없음 | 7.339–7.939 | 12.731–14.125 |

범위는 조건별 측정 3회의 최솟값–최댓값이며 원시 클라이언트 지연 표본에서
실행기가 출력한 값입니다. mutex 조건을 포함한 총 18회 모두 송신 6,000건·수신
30,000건이고 누락·중복·예상 밖 수신·클라이언트 실패는 0입니다. 서버는 각 조건
최종 peer_closed 80건, socket_error 0건입니다. 누적 서버 통계는 warm-up,
준비와 모든 반복·연결 정리를 포함하며 run별 값이 아닙니다. 실행기 출력의
`server_stats=unavailable`은 이 서버 카운터들이 0이라는 뜻이 아닙니다.

서버 설정 대조에서 약 40ms의 p99가 줄어든 결과는 캡처 유무 양쪽에서
관측됐습니다. 다만 실행 순서를 무작위화한 여러 독립 세션의 통계 검정은
아닙니다. 캡처 없는 설정 변경 결과가 캡처 있는 결과보다 느렸으므로 캡처의
영향을 일정한 비용으로 환산하거나 두 결과를 같은 분포로 취급하지 않습니다.
과거 측정의 p99 69ms 전부가 Nagle 때문이라는 결론도 내리지 않습니다.

무캡처 조건에서 기준 서버/클라이언트 CPU 시간은 12.21/28.13초,
서버 TCP_NODELAY 조건은 10.52/23.00초였습니다. 각각 약 121초의 준비·warm-up·
전체 반복 동안 사용한 CPU 시간이며, 평균 CPU 비용이 개선됐다는 일반적
결론으로 사용하지 않습니다. 두 실행의 컨테이너 cpu.stat에서 nr_throttled와
throttled_usec 증가는 모두 0이었습니다. 이는 해당 컨테이너 quota 관측이며
VM 밖의 스케줄링 대기나 공유 자원 영향을 배제하지 않습니다.

## RoomService 잠금 측정

별도 소스 사본에서 RoomService의 모든 lock_guard를 진단 guard로 바꿨습니다.
steady_clock으로 lock 직전·획득 직후·unlock 직전 시각을 읽고, 잠금을 해제한
뒤 스레드별 사전 예약 메모리에 표본을 저장했습니다. 출력은 스레드 종료 시에만
수행했습니다. 스레드별 100,000개 한도를 넘으면 drop을 세며 이번에는 4개
스레드의 drop이 모두 0입니다. 준비·warm-up·측정·연결 정리 전체를 포함합니다.

| 작업 | 표본 | 획득 대기 p99 / 최대 | 보유 p99 / 최대 |
| --- | ---: | ---: | ---: |
| chat | 24,000 | 0.333 / 601.292µs | 3.000 / 612.833µs |
| createRoom | 16 | 0.125 / 0.125µs | 12.209 / 12.209µs |
| joinRoom | 64 | 0.125 / 0.125µs | 15.458 / 15.458µs |
| attachUser | 80 | 13.000 / 13.000µs | 0.791 / 0.791µs |
| disconnect | 80 | 0.250 / 0.250µs | 23.833 / 23.833µs |

전체 분포는 [mutex-summary.json](mutex-summary.json), 원시 표본은
[압축 NDJSON](mutex-samples.ndjson.gz)에 있습니다. 표본이 적은 준비 작업은
nearest-rank p99와 최대값이 같을 수 있습니다. 단위 표기가 실제 시계의 정밀도를
보장하지는 않습니다. 보유 시간은 unlock 자체의 실행 시간을 제외합니다.

진단 빌드에서도 클라이언트 p99는 41.607–42.284ms로 재현됐습니다. 측정한
RoomService 잠금의 대기·보유에는 40ms 구간이 없었습니다. 이 조건에서 단일
mutex가 해당 지연의 주원인이라는 근거는 없습니다. 계측이 스케줄링에 영향을
주고, 다른 mutex·queue와 다른 부하 수준은 측정하지 않았으므로 일반적인
무경합이나 확장성을 입증하는 결과는 아닙니다.

## 해석 범위와 결정

이번 조건은 약 200개 채팅 요청/초이며 최대 처리량 측정이 아닙니다. 과거
69ms 표본 전체나 서버 측 TCP_NODELAY 적용 뒤 남은 지연을 하나의 원인으로
설명하지 않습니다. scheduler, VM의 공유 자원, queue 대기와 클라이언트 수신
처리는 추가 측정 대상입니다.

다음 변경은 서버가 수락한 TCP 연결에 TCP_NODELAY를 적용하는 작은 변경으로
한정합니다. 회귀 테스트와 함께 송신 패킷 수·CPU 비용, 단일 방과 slow-client,
원격 네트워크를 재검증해야 합니다. RoomService의 mutex 분할이나 shard 도입은
이 낮은 부하 결과만으로 진행하지 않습니다.

## 검증

기준 GCC 13.3 Release 빌드와 Linux 테스트 288개를 통과한 뒤 측정했습니다.
패킷 분석의 메시지 수, 실행 종료 코드, 서버 종료 통계와 mutex 표본 수를
원시 자료와 대조했습니다. 추출 pcap의 sequence/ACK·시각은 tcpdump로 다시
확인했습니다. 정적 검사 결과와 원시 로그 해시는
[validation.json](validation.json)에 기록합니다. 제품 코드 변경이 없으므로
새 회귀 테스트를 추가하지 않았으며, 기본 TCP 설정 적용 시 추가합니다.
