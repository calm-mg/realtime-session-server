# 서버 TCP_NODELAY 적용과 1차 회귀 검증

[지연 분석](../2026-09-08-latency-analysis/README.md)에서 확인한 약 40ms ACK
대기를 줄이기 위해 서버가 수락한 TCP 연결에 TCP_NODELAY를 적용했습니다.
서버 I/O 스레드가 non-blocking 설정과 함께 처리하고, 초기화에 실패한 fd는
세션에 등록하지 않고 닫습니다. 클라이언트 설정과 queue 상한, 오류 분류는
유지합니다.

## 기준과 방법

- 기준 소스: `38c8faa4714bf3b37bbd5c116f496e547ac6845d`
- 적용 후: 위 소스에 이 문서와 같은 커밋의 TCP 설정·회귀 테스트 변경 적용
- Ubuntu 24.04 arm64, GCC 13.3.0 Release, Linux 5.15.49-linuxkit-pr
- 서버·부하 생성기는 별도 프로세스, 각각 CPU 0–1과 2–3, worker 2개
- 실행 컨테이너 CPU quota 4개·메모리 4 GiB, 별도 PostgreSQL 16.15는
  CPU 0–1·quota 1개·메모리 1 GiB
- 외부 단일 방·다중 방: 20명, client별 300건, payload 256바이트,
  rate 10건/초, max-in-flight 8, timeout 60초; 다중 방은 4개 방
- 조건마다 새 서버에서 warm-up 1회 후 측정 3회, 전후를 순서대로 실행
- 서버 NDJSON은 10초 주기와 SIGTERM 종료 시 수집
- tcpdump는 CPU 2–3에서 loopback 캡처, 종료 전 1초 대기 후 정지
- 다중 방은 전체 패킷 캡처, 단일 방 최종 비교는 96바이트 헤더만 컨테이너
  내부에 저장하고 측정 종료 후 복사
- 빌드·테스트·GUI 데모는 부하 측정과 동시에 실행하지 않음

느린 클라이언트는 서버 통계가 필요한 내장 모드를 사용했습니다. 20명 중
정상 19명, payload 1291바이트, worker 2개이며 나머지 속도·반복 조건은
같습니다. 프로세스 전체를 CPU 0–3에서 실행해 외부 모드의 CPU 분리 비용과
직접 비교하지 않습니다.

[experiments.json](experiments.json)에 실행·집계 스크립트를,
[results.json](results.json)에 명령·원시 출력·서버 통계·CPU 시간·패킷 수와
실행 파일 및 전체 pcap 해시를 보관합니다. 부하 실행기의 `commit=unknown`은
소스 mount 빌드의 표시이므로 위 소스 상태와 해시를 함께 사용합니다.
실행기는 내장 서버 코드도 포함하므로 외부 모드의 클라이언트 로직 변경이
없어도 실행 파일 해시는 전후에 달라집니다.

## 전후 결과

표의 p99는 warm-up을 제외한 세 측정의 최솟값–최댓값입니다.

| 조건 | 변경 전 p99 (ms) | 변경 후 p99 (ms) | 매회 송신 / 정상 수신 |
| --- | ---: | ---: | ---: |
| 외부 다중 방 | 41.661–42.154 | 1.707–2.065 | 6,000 / 30,000 |
| 외부 단일 방, 헤더 캡처 | 40.432–40.561 | 14.035–18.987 | 6,000 / 120,000 |
| 내장 slow-client | 43.676–45.515 | 12.352–20.032 | 5,700 / 108,300 |

전후 6조건의 측정 18회에서 누락·중복·예상 밖 메시지·실패 클라이언트가 모두
0입니다. 외부 서버 네 개의 최종 누적 통계는 각각 peer_closed 80,
socket_error 0, 남은 세션 0입니다. slow-client는 매회 느린 연결 1개만
pending write 상한으로 종료됐고 정상 클라이언트 메시지는 모두 수신했습니다.

| 외부 조건 | 서버 CPU 초, 전 → 후 | 클라이언트 CPU 초, 전 → 후 | 서버 데이터 패킷, 전 → 후 | 전체 캡처 패킷, 전 → 후 |
| --- | ---: | ---: | ---: | ---: |
| 다중 방 | 1.88 → 1.85 | 6.098 → 5.338 | 92,880 → 120,521 | 208,884 → 210,171 |
| 단일 방 | 12.53 → 13.22 | 81.432 → 67.755 | 414,326 → 482,006 | 852,917 → 757,324 |

서버 데이터 패킷은 다중 방에서 약 29.8%, 단일 방에서 약 16.3% 증가했습니다.
단일 방 서버 CPU 시간은 약 5.5% 증가했습니다. 전체 패킷 수에는 ACK도
포함되므로 서버 데이터 패킷 수와 같은 방향으로 움직이지 않을 수 있습니다.
최종 비교의 네 캡처 모두 커널 누락과 RST가 0입니다.

재측정의 단일 방 지연·CPU 값은 아래 첫 시도와 차이가 큽니다. 캡처가 실행
타이밍과 자원 사용에 영향을 준다는 한계도 드러나므로, 첫 시도의 낮은 변경 후
p99만 대표값으로 선택하지 않았습니다. 같은 캡처 방식의 전후 비교만 제시하고
원격 환경이나 무계측 성능으로 일반화하지 않습니다.

## 캡처 재시도

단일 방의 첫 전후 실행은 전체 payload를 공유 디렉터리에 기록하다가 각각
949,497개와 926,447개의 커널 캡처 누락이 발생했습니다. 메시지 검증은
통과했지만 불완전한 캡처이므로 비용 비교에서 제외하고 원시 결과를 남겼습니다.
96바이트 헤더 캡처와 컨테이너 내부 저장으로 같은 조건을 다시 실행했습니다.
헤더 캡처의 payload 바이트 수는 캡처 길이가 아니라 IPv4 total length에서
IP·TCP 헤더 길이를 뺀 값입니다.

## 결과 해석

외부 서버 통계는 준비·warm-up·모든 측정 반복·연결 정리의 누적 값입니다.
`server_stats=unavailable`을 카운터 0으로 해석하지 않습니다. 느린 클라이언트
결과의 서버 snapshot은 내장 실행기의 수집 시점 기준입니다.

CPU 시간은 준비와 warm-up을 포함한 전체 실행의 user+system 누적 시간입니다.
클라이언트는 wait4/rusage, 서버는 종료 직전 /proc/PID/stat에서 수집했습니다.
서버 시작과 종료 정리 구간까지 완전히 동일한 범위의 CPU 표본은 아닙니다.
캡처는 양쪽 조건에 동일하게 적용했지만 스케줄링에 영향을 줄 수 있습니다.

데이터 패킷 수는 loopback에서 캡처한 TCP payload가 있는 패킷 수이며 ACK만
있는 패킷은 제외합니다. 재전송·준비·퇴장 알림도 포함하고, offload와 묶음
처리의 영향을 받으므로 실제 외부 NIC 패킷 수로 일반화하지 않습니다.

이 결과는 지정한 낮은 부하의 회귀 비교입니다. 최대 처리량, 원격 네트워크,
장시간 안정성과 남은 지연 전체의 원인을 입증하지 않습니다. 비용과 성능이
모든 환경에서 같은 비율로 달라진다는 뜻도 아닙니다.

## 회귀 테스트와 검증

실제 서버의 수락 소켓을 /proc/self/fd에서 주소·포트로 찾아 getsockopt로
확인하는 테스트를 추가했습니다. 클라이언트 옵션을 확인하는 테스트가 아니며,
세 번 새로 연결해 모두 TCP_NODELAY=1인지 확인합니다. 지연 임계값이나 sleep
길이로 성공을 판단하지 않습니다. 기존 서버에서는 세 연결 모두 0으로 실패했고
설정 적용 후 통과했습니다.

기준 테스트 중 기존 외부 실행기 검사의 snapshot 경합도 관측했습니다.
서버는 거절 연결을 close한 뒤 카운터를 갱신하므로, 클라이언트가 close를 본
직후에는 카운터가 아직 0일 수 있습니다. 테스트가 서버 I/O 스레드 종료를
기다린 뒤 최종 snapshot을 확인하도록 보강했습니다. 서버의 카운터 순서나
분류는 바꾸지 않았습니다.

검증 명령·결과와 초기 실패의 구분은 [validation.json](validation.json)에
기록합니다. 추가 성능 연구는 1차 완료의 필수 조건에 넣지 않습니다.
