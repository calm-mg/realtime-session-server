# 로드맵

이 문서는 아직 착수하지 않은 기능과 성능 개선 방향을 정리합니다. 현재
우선순위와 완료 상태는 [프로젝트 상태](project-status.md), 확인된 결함은
[알려진 문제](known-issues.md)를 기준으로 합니다. 여기에는 현재 작업의
세부 완료 조건이나 해결 이력을 중복해서 기록하지 않습니다.

## 1단계: 정확성과 운영 기반

- 프로젝트 상태에서 선택한 서버 상태 계약과 열린 운영 결함을 모두 해결
- 장애와 과부하 상태를 외부에서 일관되게 관측할 수 있는 운영 인터페이스
  제공

이 단계에서는 새 사용자 기능보다 기존 상태의 일관성과 장애 시 동작을
우선합니다.

## 2단계: Qt 클라이언트 완성도

- 프로젝트 상태에서 선택한 요청 상태와 메모리 상한 작업 완료
- 방 목록과 현재 사용자 목록
- 위치 업데이트 입력과 시각화
- PING 왕복 지연 시간 화면
- 선택적인 자동 재접속과 로그인·방 상태 복구

자동 복구는 서버 상태와 중복 요청 정책을 먼저 정의한 뒤 추가합니다.

## 3단계: 프로토콜과 보안

- 문자열 필드의 UTF-8 및 escape 규칙
- 프로토콜 버전과 호환성 정책
- 최대 크기와 오류 응답 규칙 정리
- TLS 적용 방식
- 인증 토큰과 세션 인증
- 영속화할 사용자·방 상태와 재시작 시 복구 범위 정의

프로토콜을 변경할 때는 `docs/protocol.md`와 서버, 콘솔 클라이언트, Qt
클라이언트 테스트를 같은 변경에서 갱신합니다.

## 4단계: 측정 기반 확장

- 재현 가능한 부하 결과의 장기 회귀 이력과 비교 기준 확립
- 반복 연결·종료, 혼합 workload와 원격 환경 측정 범위 검토
- `RoomService` mutex 경합 측정 후 방 단위 잠금 또는 shard 결정
- `TcpServer`의 connection, inbound, outbound와 shutdown 책임 분리 검토
- 다중 I/O 스레드 또는 `io_uring`은 단일 I/O 스레드의 병목이 측정된 뒤
  검토
- Qt 설치 패키지(DMG, MSI, AppImage) 생성

구조 변경은 추측이 아니라 재현 가능한 부하 결과와 profiling 근거가 있을
때 진행합니다.

현재 부하 도구와 비교 제약은 [벤치마크 가이드](benchmark.md)를 참고합니다.

## 로드맵 밖의 현재 범위

- 모바일 UI와 QML 전환
- 서버의 Windows 또는 macOS 네이티브 네트워크 backend
- 분산 데이터베이스나 다중 지역 배포

필요성이 생기면 별도 설계 문서에서 요구사항과 비용을 먼저 검토합니다.
